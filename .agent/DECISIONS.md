# Agent Decisions

- (template) Record backward-compatible default decisions here with date, context, and rationale.
- 2026-05-05: Daily quest MVP policy.
  - Add a Duolingo-like daily quest layer as a backward-compatible additive feature.
  - Use the existing server-authoritative today study queue as the source for quest cards; do not create a new scheduling engine and do not compute `due_at` on clients.
  - Expose quest data through a new authenticated additive endpoint rather than changing `/study/today`.
  - Default daily quest target is 5 cards. Completed progress is based on distinct study/review items completed today and capped by the daily target for display.
  - Quest day count is the existing distinct study/review day count. Memorized word count uses the existing distinct mastered memory item count.
  - The Chrome extension popup may show quest progress before quiz start, but review submission, pending queue, token, and auth behavior remain unchanged.
  - The feature must not delete or mutate `review_logs`, `review_states`, legacy words, or learning events.
- 2026-05-05: Mobile app decisions.
  - Architecture: Mobile app lives in `apps/mobile`; use Expo + React Native, Expo Router, and pnpm workspace. Reuse `packages/core` for shared study types, ratings, session engine, and pending review event model where practical. Do not duplicate scheduler logic in mobile; the server remains authoritative for scheduling and `due_at` calculation.
  - Mobile MVP scope: Initial mobile scope is study-focused. Include login/register, today study, review submission, pending review queue, mistakes, profile summary, and settings/logout. Exclude full wordbook CRUD, Markdown import/export, course admin, teacher dashboard, group management, and paid content admin from the mobile MVP.
  - Auth: Store auth token in `expo-secure-store`; do not store auth token in AsyncStorage. Non-sensitive settings may use AsyncStorage. If token is missing or invalid, show login flow.
  - API: Use `EXPO_PUBLIC_API_BASE_URL` for API base URL. iOS simulator may use localhost; Android emulator may need `10.0.2.2`; physical devices need LAN IP or deployed API URL. Do not add mobile-specific API endpoints unless existing APIs are insufficient.
  - Study: Mobile reviews must use `StudyPlatform.MOBILE`, include `clientEventId`, and submit through `POST /study/cards/{cardId}/review`. Mobile must not compute final schedule or `due_at` locally.
  - Pending review queue: Store pending review queue in AsyncStorage or equivalent non-sensitive storage. Reuse the `packages/core` pending review event shape where practical. Keep `clientEventId` stable across retries. Use the same retry/status-code policy as Chrome extension: success removes event; network/5xx keeps event and increments `attemptCount`; 401/403 keeps queue and requires login; 404/409/422 removes event. Keep up to 7 days, cap at 200 events, flush oldest first, and flush at most 20 events per run.
  - UX: Mobile should feel like a daily study app, not an admin dashboard. Home emphasizes today review count and primary "오늘 복습 시작" action. Study screen uses card-based layout, large tap targets, and simple loading/error/empty states.
- 2026-05-05: Mobile workspace React type isolation. Expo SDK 54 mobile uses React 19 while the existing web app remains React 18. Do not enable workspace-wide `nodeLinker: hoisted` because it can mix React runtime instances and break web tests. Keep pnpm's existing isolated workspace behavior. If React type declarations leak between mobile and web through shared dependency type resolution, scope the web TypeScript resolver to the web app's local React 18 type package instead of upgrading the web app or downgrading mobile.
- 2026-05-05: Extension web auth entry points. The extension does not implement a separate auth flow; popup/options login and registration actions open the configured web app (`VITE_WEB_APP_URL`, default `http://localhost:5173`) with `auth=login|register` and `source=extension`. The web app remains the source of credential handling, and the extension continues to store the token only through the existing content-script `MEMORY_NOTE_AUTH_TOKEN` handoff. This is backward-compatible and avoids duplicating authentication UI or changing existing token/API semantics.
- 2026-05-05: T15 analytics / recommendation defaults. Phase 15 uses read-only analytics derived from existing `review_logs`, `review_states`, `cards`, and `memory_items`; it does not mutate or delete learning data. New analytics are exposed through additive optional fields and a new authenticated analytics endpoint. Today queue recommendation improvements are represented as optional per-card reason/score fields while preserving the existing ordering contract. Card quality and content quality signals are conservative heuristics based on review volume, recall rate, lapses/leech score, missing example sentences, and inactive/deleted exclusions. If there is no data, return zero-safe counts/rates rather than failing.
- 2026-05-05: T14 paid course / entitlement policy. Phase 14 implements paid course access structure without real payment provider integration. `user_entitlements` is the source of truth for paid course access. `products` may reference `course_packs`, use product type `COURSE_PACK`, and support `DRAFT`, `ACTIVE`, `ARCHIVED`. `user_entitlements` supports status `ACTIVE`, `REVOKED`, `EXPIRED` and source `MANUAL`, `PURCHASE`, `CLASS_LICENSE`; only MANUAL/test/internal grants are implemented in this phase and PURCHASE remains schema-ready only. Free course packs are accessible without entitlement; paid course packs require ACTIVE entitlement, and revoked/expired entitlements do not grant access. Course start creates or links user-owned learning state without mutating source course content, duplicating review_logs, deleting legacy words, learning_events, review_logs, or review_states. Refund behavior is modeled only as entitlement revoke; real provider refund APIs are deferred. Because no secure admin/role system exists, unsafe public admin routes are not exposed; admin basics are limited to internal service functions and tests.
- 2026-05-05: T13 teacher classes privacy default. Teacher classes are private. Creating a class makes the creator an active TEACHER. Added students start as PENDING and must accept before assignments are visible or their activity can be included. Teacher dashboards return aggregate assignment progress only, not per-student review details. Assignments can reference only the teacher's own wordbooks, do not copy/delete/mutate student review state, and report zero-safe progress when no matching review data exists.
- 2026-05-05: T12 study groups privacy default. Study groups are private by default. Creating a group makes the creator an active OWNER. Added users start as PENDING members and must accept before their data is included. Group progress only aggregates active members' wordbooks that those same users explicitly linked to the group. Group weak-card detail returns only the requesting active member's own linked cards, so prompts/answers from other users are not exposed by default. Owner-only actions are member invite/removal; all group reads require at least membership, and progress/weak-card reads require ACTIVE membership.
- 2026-05-04: T4.5 profile 통계 호환 정책 적용. legacy learning_events 필드는 유지하고, review_logs/review_states 데이터가 있으면 우선 사용하되 중복은 memory_item_id > word_id > card_id 순서로 제거한다. API 응답 shape은 유지하고 확장 필드는 optional로 추가한다.
- 2026-05-04: T5.5 pending review queue 정책 반영. chrome.storage.local `pendingReviewQueue` 사용, 7일 보관/최대 200건 유지, flush 시 oldest-first 최대 20건 전송, 401/403은 큐 보존 후 중단, 404/409/422는 드롭, 네트워크/5xx는 재시도 카운트 증가.
- 2026-05-04: T6.1 MASTERED 정책 확정. REVIEW 상태에서만 interval_days>=30, streak>=5, lapses<=1, (difficulty 존재 시 <=0.7)일 때만 MASTERED 전환. difficulty가 null이면 차단하지 않음. MASTERED에서 AGAIN 시 RELEARNING/10분 due/lapses+1/streak=0/leech+2/last_reviewed_at 갱신, mastered_at은 유지.
- 2026-05-04: T6.2 장기 MASTERED 샘플링 정책 적용. /study/today에서 MASTERED 카드 장기 점검 슬롯을 limit의 10%(최소 1, 최대 limit)로 포함하고, 최근 7일 복습한 MASTERED는 제외, due된 MASTERED는 일반 due 카드로 처리. 정렬 우선순위는 last_reviewed_at(오래된 순) -> mastered_at -> card created/updated, 중복 카드 제외 및 memory_item 연속 최소화를 유지.
- 2026-05-05: T6.4 long-term memory stats 정책 적용. 기존 `/profile/summary` 응답 shape과 기존 필드 의미는 유지하고 장기 기억 통계는 optional 확장 필드(`masteredCount`, `longTermReviewCount30d`, `longTermCorrectCount30d`, `longTermRecallRate30d`, `masteredLapseCount30d`, `oldMasteredDueCount`)로만 추가한다. 기본 보고 기간은 최근 30일이며 review_logs/review_states를 우선 source of truth로 사용한다. `review_logs`는 삭제/변경하지 않고 null-safe 계산을 적용한다. 장기 리뷰 판정은 `state_before_json.status == MASTERED`를 우선하고, 값이 없을 때 안전하면 현재 `review_state.status == MASTERED`로 fallback한다. 같은 종류의 사소한 metric-definition ambiguity는 안전한 optional-field 기본값을 선택할 수 있으면 앞으로 hard blocker로 멈추지 않는다.
- 2026-05-05: T7 FSRS scheduler 도입 기본값. `SchedulerService.review(state, rating, reviewed_at)` 인터페이스와 기존 API 동작은 유지하고, 새 FSRS 계열 엔진은 `SCHEDULER_ENGINE=fsrs`로 선택할 수 있게 한다. 기본값은 backward-compatible하게 `simple`이며, 잘못된 값은 `simple`로 fallback한다. `retrievability`는 DB 컬럼으로 저장하지 않고 `ReviewState.last_reviewed_at`과 `stability`에서 계산한다.
- 2026-05-05: T8 word-to-sentence cards 정책 적용. 기존 Word API shape은 optional `exampleSentence`로만 확장한다. `WORD` 타입 memory_item에 예문이 있으면 기본 양방향 카드에 더해 `CLOZE`(예문 안 key/value 첫 일치 항목을 `____`로 치환, 없으면 예문+blank)와 `TYPING`(예문 prompt, key answer, value hint) 카드를 생성한다. 예문이 제거되거나 item type이 바뀌면 기본 생성 관리 대상 카드(`BASIC_*`, `CLOZE`, `TYPING`) 중 더 이상 원하는 카드가 아닌 것은 비활성화하되 review_logs는 유지한다.
- 2026-05-05: T9 Markdown v2 / course pack 기본 경계. Markdown v1(`key/value/lastViewedAt`)는 계속 호환하고, v2는 optional 컬럼(`itemType`, `exampleSentence`/`sentence`, `tags`, `cloze`)만 추가로 해석한다. `tags`는 comma/semicolon 구분 문자열로 받는다. `cloze`는 별도 학습 상태를 만들지 않고 예문 기반 CLOZE 카드의 metadata로만 보존한다. Course pack은 사용자 review state와 분리된 content-only 구조(`course_packs`, `course_units`, `course_lessons`, `course_lesson_items`)로 먼저 추가하며, 사용자 단어장으로 복사/시작하는 흐름과 권한/판매 정책은 후속 phase에서 다룬다.
- 2026-05-05: T11 study events 기본 정책. `study_events`는 review 이후 생성되는 append-only UX event log이며 review_logs/review_states의 source of truth를 바꾸지 않는다. 기본값은 `funEventsEnabled=true`이고, 사용자가 끄면 새 study_event를 생성하지 않는다. 이벤트 타입은 보수적으로 `MASTERED`, `MASTERED_LAPSE`, `LEECH`, `ZOMBIE_REVIEW`만 추가하며 API 응답 shape은 설정 endpoint와 optional user field로만 확장한다.
