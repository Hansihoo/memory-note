# DELIVERY_LOOP

## 목적
개발을 작은 반복 단위로 끊어 사용자와 계속 대화하면서 진행하기 위한 표준 루프다.

## 시작 전 전제
- 개발 회차를 시작하기 전에 기능 명세와 개발 전달 문서가 있어야 한다.
- 이번 회차 범위는 그 문서 안에서 가장 작은 구현 단위로 자른다.

## 기본 루프
1. 이번 회차 범위 합의
2. 코드 수정
3. build / test / lint / typecheck
4. 로그와 동작 확인
5. 문제 있으면 재수정
6. 간략 문서화
7. 다음 회차 제안

## Codex 반복 검증 루프
1. acceptance criteria를 이번 회차 테스트 목록으로 바꾼다.
2. 구현 전 실패가 예상되는 테스트 또는 수동 확인 시나리오를 정한다.
3. 구현한다.
4. format, lint, typecheck를 먼저 실행한다.
5. 관련 unit/integration/e2e 테스트를 실행한다.
6. 실패하면 디버그 로그를 필요한 영역에만 켠다.
7. 실패 위치를 프런트, API, DB, parser, session state 중 하나로 좁힌다.
8. 수정한다.
9. 같은 명령을 다시 실행한다.
10. 통과하면 디버그 로그가 기본값에서 꺼져 있는지 확인한다.
11. 검증 결과와 남은 위험을 문서에 남긴다.

## 한 회차에 포함해야 할 것
- 이번 회차 목표
- 참조한 기능 명세 / 개발 전달 문서
- 변경 대상 파일 또는 영역
- 실행한 명령
- 검증 결과
- 발견된 문제
- 다음 회차 후보

## 회차 크기 기준
- 한 번에 하나의 작은 사용자 가치 또는 하나의 작은 기술 목표
- 여러 화면, 여러 API, 여러 정책 변경을 한 회차에 몰지 않는다
- 실패했을 때 되돌리기 쉬운 단위로 나눈다

## 검증 기본안
- 구현 후 `build`, `test`, `lint`, `typecheck` 중 관련 항목을 수행한다.
- UI/UX가 바뀌면 실제 화면 확인 또는 로그 확인을 남긴다.
- 실패한 명령이 있으면 무시하지 말고 원인과 다음 조치를 남긴다.
- import/export는 parser golden test와 round-trip test를 우선한다.
- 암기 세션은 state unit test와 e2e를 함께 둔다.
- 프로필 누적 학습일은 날짜 계산 unit test와 timezone 경계 테스트를 둔다.

## 로그 기본안
- 상세 로그는 기본 OFF다.
- production은 `LOG_LEVEL=warn` 이상을 기본으로 한다.
- 디버그 로그는 `DEBUG_IMPORT`, `DEBUG_SESSION`, `DEBUG_PROGRESS`, `DEBUG_SYNC` 같은 기능별 플래그로 켠다.
- 로그는 문제 위치를 좁히는 목적에 한정하고, 성능에 영향을 주는 문자열 조립은 guard 뒤에서만 한다.
- 단어 내용, 답변 내용, 사용자 토큰, 민감정보는 로그에 남기지 않는다.

## 반복 중단 기준
- 같은 검증이 3회 이상 실패하면 원인 가정과 범위를 다시 정리한다.
- 인증, 삭제, 동기화 충돌, 민감정보 처리처럼 정책 결정이 필요한 경우 사용자 확인에서 멈춘다.
- 테스트는 통과하지만 사용자 흐름이 기획 의도와 맞지 않으면 개발을 멈추고 기획 문서로 되돌린다.

## 문서화 기본안
- 회차마다 긴 문서를 새로 쓰지 않는다.
- 바뀐 규칙, 명령, 결정만 짧게 반영한다.
- 구현보다 문서가 뒤처지지 않게 한다.

## 다음 회차로 넘길 때 남길 것
- 완료된 것
- 보류된 것
- 추가 질문
- 다음 회차 추천 시작점

## Codex에 말할 수 있는 예시
- `이번 회차는 로그인 화면 폼 검증만 구현하고 검증까지 진행하자`
- `이전 작업 다음 사이클을 진행하자. build, test, logs까지 확인해줘`
- `이 에러를 재현하고 수정 후 회귀 확인까지 이번 회차에서 처리하자`
- `이 기능 명세를 기준으로 첫 개발 회차를 시작하자`
