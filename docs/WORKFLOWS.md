# WORKFLOWS

## 상위 진행 흐름
이 문서는 개별 workflow뿐 아니라, Codex가 현재 상태를 보고 어떤 다음 단계로 이어가야 하는지도 함께 정의한다.

1. 초기 설정
2. 기획 회차
3. 개발 전달 정리
4. 개발 회차
5. 유지보수 또는 릴리즈/CI
6. 문서 동기화와 다음 회차 시작점 정리

사용자는 보통 현재 하고 싶은 일만 말하면 된다. Codex는 관련 문서와 미확정 항목을 보고 위 흐름 중 현재 단계와 다음 단계를 스스로 고른다.

## 자동 진행 규칙
1. 현재 작업을 막는 `{{PLACEHOLDER}}` 또는 정책 미확정이 있으면 먼저 짧게 질문한다.
2. 현재 작업을 막는 값이 없으면, 사용자가 다시 "다음"이라고 말하지 않아도 가장 가까운 다음 유효 단계로 이어간다.
3. 각 회차가 끝나면 결과를 문서에 반영하고, `이번 회차 결정`, `남은 질문`, `다음 회차 시작점`을 남긴다.
4. 다음 회차 시작점이 명확하고 위험한 결정이 없으면 그 시작점까지 자동으로 이어서 진행한다.
5. 아래 항목은 자동으로 넘기지 않고 사용자 확인에서 멈춘다.
   - 실제 서비스 범위를 템플릿 범위 밖으로 확장하는 결정
   - 배포 승인, 운영 정책, 민감정보 처리 같은 고위험 결정
   - 현재 작업을 직접 막는 핵심 미확정값

## 단계 전이 기준
- 초기 설정 -> 기획 회차:
  - 현재 작업에 영향을 주는 placeholder가 정리됐고, 문제 정의를 시작할 수 있을 때
- 기획 회차 -> 다음 기획 회차:
  - 이번 단계 결과가 문서화됐고, 다음 질문 묶음이 남아 있을 때
- 기획 회차 -> 개발 전달 정리:
  - 핵심 사용자, 주요 흐름, 범위, 성공 조건이 개발 가능한 수준까지 정리됐을 때
- 개발 전달 정리 -> 개발 회차:
  - 기능 명세와 handoff가 있고, 이번 회차의 최소 구현 범위와 검증 명령이 정리됐을 때
- 개발 회차 -> 다음 개발 회차:
  - 이번 변경과 검증 결과가 기록됐고, 다음 시작점이 남아 있을 때
- 어느 단계에서든 -> 유지보수:
  - 버그, 회귀, 장애 재현 요청이 들어왔을 때
- 어느 단계에서든 -> 릴리즈/CI:
  - 배포 점검, release gate, 롤백 검토 요청이 들어왔을 때

## 기획 workflow
1. 관련 `{{PLACEHOLDER}}`가 있으면 먼저 질문하고 확정 여부를 구분한다.
2. 이번 회차에서 다룰 기획 단계 하나만 정한다.
3. 사용자 문제와 사용 사례를 정리한다.
4. 목표와 비목표를 구분한다.
5. UX 시나리오와 실패 시나리오를 적는다.
6. 필요한 화면, API, 데이터 모델 후보를 적는다.
7. 미확정 항목을 질문지로 되돌린다.
8. 결과를 `PROJECT_PROFILE` 또는 별도 기획 문서에 반영한다.
9. 다음 기획 회차 질문을 남긴다.
10. 개발 가능 수준이 되면 기능 명세와 개발 전달 문서 초안을 만든다.

## 기능 개발 workflow
1. 현재 기능에 필요한 값이 미확정이면 먼저 질문한다.
2. 기능 명세와 개발 전달 문서가 준비됐는지 확인한다.
3. 이번 회차 구현 범위를 작은 단위로 좁힌다.
4. 요구사항이 문서로 확정됐는지 확인한다.
5. 작업 범위와 비범위를 적는다.
6. 구현 전 영향을 받는 명령과 검증 항목을 확인한다.
7. 코드 수정 후 build, test, lint, typecheck를 수행한다.
8. 로그와 동작 흐름을 확인한다.
9. 문제가 있으면 같은 회차에서 가능한 범위까지 재수정한다.
10. 문서와 명령 예시를 함께 갱신한다.
11. 다음 개발 회차 시작점을 남긴다.

## Codex 개발 검증 수정 workflow
1. 이번 회차 acceptance criteria를 테스트 항목으로 바꾼다.
2. 프런트, 백엔드, DB, parser, session state 중 어디가 영향을 받는지 먼저 적는다.
3. 구현한다.
4. 정적 검사를 먼저 실행한다.
5. unit, integration, e2e 중 관련 테스트를 실행한다.
6. 실패하면 필요한 디버그 플래그만 켜고 로그를 확인한다.
7. 문제 위치를 좁혀 수정한다.
8. 같은 검증 명령을 다시 실행한다.
9. 통과 후 디버그 로그 기본값이 OFF인지 확인한다.
10. 결과, 실패 원인, 수정 내용, 남은 위험을 개발 회차 문서에 남긴다.

## 로그 운영 workflow
1. 평소에는 상세 로그를 남기지 않는다.
2. 디버깅이 필요할 때만 기능별 플래그를 켠다.
3. import, session, progress, sync처럼 영역별 로그를 분리한다.
4. request id로 프런트와 백엔드 흐름을 연결한다.
5. 민감정보와 단어 내용은 로그에서 제외한다.
6. 배포 전 production 기본 로그 레벨과 디버그 플래그 OFF를 확인한다.

## 버그 수정 workflow
1. 재현에 필요한 정보가 부족하면 먼저 질문한다.
2. 재현 조건을 먼저 적는다.
3. 기대 동작과 실제 동작을 분리한다.
4. 원인을 코드, 설정, 데이터, 환경 중 어디인지 좁힌다.
5. 수정 후 재현 케이스와 인접 회귀를 다시 확인한다.
6. 필요한 경우 운영 문서와 FAQ를 갱신한다.

## 유지보수 workflow
1. 현재 경고를 처리하는 데 필요한 정책값이 미확정이면 먼저 질문한다.
2. 의존성, 빌드, 테스트, 배포 경고를 수집한다.
3. 위험도와 영향 범위를 기준으로 우선순위를 정한다.
4. 자동 수정 가능한 항목과 수동 검토 항목을 구분한다.
5. 변경 후 표준 명령으로 회귀를 확인한다.
6. 변경 사유와 후속 TODO를 문서화한다.

## CI/CD workflow
1. 배포 대상, 승인 방식, 환경 구성이 미확정이면 먼저 질문한다.
2. PR 기준 필수 검증을 정의한다.
3. Preview 생성 여부와 조건을 확인한다.
4. main 반영 전 배포 영향 범위를 확인한다.
5. Production 배포 시 롤백 조건과 모니터링 포인트를 적는다.
6. 배포 후 로그, 헬스체크, 핵심 사용자 흐름을 다시 확인한다.

## 권장 운영 원칙
- 문서 없는 구현보다 문서 있는 느린 진행이 낫다.
- 자동화는 검증 가능한 단위부터 켠다.
- workflow는 프로젝트가 커질수록 더 짧고 반복 가능해야 한다.
- 한 번의 대화에서 전체 로드맵을 끝내기보다 다음 유효 단계가 명확한 상태를 더 중요하게 본다.
- 자동 진행은 "다음 단계가 명확할 때 이어서 진행"을 뜻하며, 미확정 정책까지 임의 확정하는 것을 뜻하지 않는다.
