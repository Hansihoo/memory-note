## 현재 확정된 항목
- 이 저장소에서 실제 개발할 제품 후보는 `암기 어시스턴트`다.
- 첫 번째 핵심 사용자는 어학 단어 학습자다.
- 핵심 가치는 사용자가 직접 만든 key/value 단어장을 반복 학습하고, 진행 상태를 추적하는 것이다.
- 단어장은 여러 개를 관리할 수 있어야 한다.
- 단어장 데이터의 기본 교환 형식은 Markdown이다.
- 단어 항목의 MVP 필수 필드는 `key`, `value`, `최근 조회한 날짜`다.
- 프로필의 학습일 지표는 `누적 학습일`을 사용한다.
- 사용자는 단어장을 직접 생성하고, Markdown 파일로 업로드하고, 필요하면 export할 수 있어야 한다.
- 사용자는 단어를 추가, 제거, 수정할 수 있어야 한다.
- 암기 화면은 key와 value 방향을 바꿔가며 질문할 수 있어야 한다.
- 암기 화면에는 `알고 있음`, `잘 모르겠음`, `정답 확인`에 해당하는 빠른 조작이 있어야 한다.
- 프로필 또는 대시보드에서는 단어장별 진행 상태와 누적 학습일을 볼 수 있어야 한다.
- AI 추천은 첫 버전에 넣지 않고 후속 기능으로 둔다.
- Markdown 포맷은 사람이 직접 쓰기보다 앱이 안정적으로 읽고 LLM이 쉽게 생성할 수 있는 구조를 우선한다.

## 우선 MVP 후보
- 웹 앱에서 회원 또는 사용자 식별 기반으로 단어장을 클라우드에 저장한다.
- 앱 클라이언트 확장을 고려하되, 첫 구현은 웹 앱과 클라우드 저장을 우선한다.
- Markdown import/export를 지원한다.
- 단어장 생성, 목록 조회, 상세 편집, 단어 삭제를 지원한다.
- 암기 세션에서 key -> value, value -> key 방향을 전환할 수 있다.
- `정답 확인`, `알고 있음`, `잘 모르겠음` 입력에 따라 최근 조회한 날짜와 학습 기록을 갱신한다.
- 단어장별 진행 상태와 누적 학습일을 보여준다.

## 후속 기능 후보
- AI를 통한 단어 추천 또는 단어장 확장
- 음성 인식으로 답변 입력
- Chrome 확장 프로그램
- Windows 앱 또는 트레이 앱
- 모바일 앱

- 고급 암기 알고리즘, 예: spaced repetition 또는 Leitner box

## 미확정 시 작업 규칙
- 현재 작업에 필요한 값이 미확정이면 먼저 질문한다.
- 구현, 배포, 자동 수정은 관련 항목이 확정된 뒤에만 진행한다.
- 결정이 늦어질 수 있는 값은 `{{PLACEHOLDER}}`와 `TODO(USER):`로 남긴다.
- 질문은 꼭 필요한 것만 짧게 하고, 사용자가 모르면 권장 기본안으로 이어간다.
- 한 번의 인터뷰에서 모든 항목을 다 묻지 않고, 답변을 바탕으로 채울 수 있는 값부터 먼저 반영한다.
- 서비스 유형이 정해지면 그 유형에 맞는 다음 질문만 이어서 묻는다.

## 권장 기본안
- 첫 출시 플랫폼: 웹 앱 + 클라우드 저장
- 인증: 이메일 또는 소셜 로그인 기반 계정
- AI 추천: MVP 이후 1.5차 기능
- 음성 인식: 후속 기능
- Chrome 확장, Windows 앱, 모바일 앱: 웹 MVP 검증 후 별도 클라이언트로 확장
- Markdown 포맷: YAML frontmatter + fenced JSON 데이터 블록
- 학습 알고리즘: 초기에는 최근 조회한 날짜와 사용자 응답 기록 기반, 이후 spaced repetition으로 확장
- 디버그 로그: 기본 OFF, `DEBUG`/`LOG_LEVEL`/기능별 플래그로 개발 중에만 활성화
- 프런트 패키지 매니저: `pnpm`
- Python 도구: `uv`
- 프런트 테스트: `Vitest` + `Playwright`
- 백엔드 테스트: `pytest`
- 린트/포맷: `ESLint` + `Prettier` + `ruff`
- 타입 검사: 프런트 `tsc`, 백엔드 `mypy`
- 로컬 실행: 루트 표준 명령 + 앱별 명령 병행
- 로그 확인: 앱 로그 + 컨테이너 로그를 루트 명령으로 통합
- 백엔드 배포: `Render` 또는 `Railway`
- 환경: `local / preview / prod`
- 배포 토폴로지: 프런트 `Vercel`, 백엔드 `Render` 또는 `Railway`, DB는 managed `PostgreSQL`
- branch 전략: `main + feature branch`
- commit 규칙: 한글 제목 + 상태 태그
- merge 방식: `squash merge`
- 기획 회차 기록: issue 또는 `docs/planning/*.md`
- 개발 회차 기록: PR 본문, changelog 성격 문서, 또는 `docs/delivery/*.md`

## 회차 운영 기본안
- 기획 회차: 문제 정의 -> 사용 사례 -> 화면 구조 -> UX/UI -> 정책/범위 -> 개발 전달
- 개발 회차: 범위 합의 -> 구현 -> build/test -> 로그 확인 -> 수정 -> 짧은 문서화
- 각 회차 결과에는 `이번 회차 결정`, `남은 질문`, `다음 회차 시작점`이 포함된다.

## 커밋 메시지 규칙 기본안
- 형식: `[태그] 변경 내용`
- 태그 예시:
  - `[기획]` 요구사항, 사용자 흐름, 화면 구조 변경
  - `[개발]` 기능 구현, 로직 변경
  - `[수정]` 버그 수정, 회귀 대응
  - `[문서]` 문서 정리, 가이드 보강
  - `[배포]` CI/CD, 배포, 릴리즈 변경
  - `[구조]` 템플릿 구조, 폴더 구조, 공통 규칙 변경
- 기획 변경이 개발에 반영되면 제목에 그 사실이 드러나게 적는다.
  - 예: `[개발] 기획 변경 반영해 암기 세션 상태 갱신 수정`
  - 예: `[문서] 기획 변경 반영해 기능 명세와 handoff 갱신`
